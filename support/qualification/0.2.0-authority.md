# Authority proof inventory for 0.2.0

This inventory implements Q-02 in the frozen [coverage manifest](0.2.0-coverage.md)
and the binding matrix required by #578. It identifies the proof locations and
remaining work; it does not mark PA-02 as passed. Candidate execution results
belong in the acceptance record, with the source, database, Job and Pod identities.

Every row applies to PostgreSQL and MySQL on both resource families unless its
contract column explicitly limits it. An admission-only or schema-only result
does not establish the corresponding operational migration result. The
[functional matrix](0.2.0-functional-matrix.md) supplies the minor, suite and
architecture dimensions; this table supplies the authority mutations inside them.

## What the SQL evidence must establish

The existing [server audit](../../test/e2e/database_audit_e2e_test.go) counts SQL
received from the exact completed runner Pod's IP. A target-binding or expired
dispatch refusal happens before executor invocation, so the required count is
zero. A positive control must produce records; an empty, truncated or disabled
journal cannot pass. Logs retain the Job and Pod UIDs and safe counters, never
raw credential-bearing SQL.

Drift and history refusals read the database to decide whether the approved
work is still authorized. Their allowed reads cannot be treated as zero SQL.
History inspection can also create an empty revision table. Record the exact
authorized diagnostic/coordination work separately from approved mutation and
verify that no unauthorized statement reached execution. A prefix classifier
that treats every SELECT or WITH statement as harmless is insufficient: either
can invoke mutating work. Database equality alone also misses attempted or
rolled-back mutations.

For a refusal before any Job exists, there is no runner Pod IP to invent. Bind
the server audit to the isolated database/credential and complete watch window;
account for legitimate read Jobs and fail on unidentified traffic. Retain the
fault's admission/persistence time, resource generation, old/new plan identity,
and the allowed control's database effects.

The absolute-dispatch-deadline row belongs to Q-03. Both migration engines now
use the same server audit to assert zero records from the completed expired
Apply Pod, with an observed History Pod as the logging control. This measures
the refusal's SQL behavior; it does not substitute for the target-recovery
control or the remaining binding rows above.
