# Authority proof inventory for 0.2.0

This inventory implements Q-02 in the frozen [coverage manifest](0.2.0-coverage.md)
and the binding matrix required by #578. It identifies the proof locations and
remaining work; it does not mark PA-02 as passed. Candidate execution results
belong in the acceptance record, with the source, database, Job and Pod identities.

Every row applies to PostgreSQL and MySQL on both resource families unless its
contract column explicitly limits it. An admission-only or schema-only result
does not establish the corresponding operational migration result. The
[functional matrix](0.2.0-functional-matrix.md) supplies the minor, suite and
architecture dimensions; this table supplies the authority mutations inside them.

## Accepted name boundary

The existing hung-result scenarios implement the name part of Q-05 in
[the schema proof](../../test/e2e/faults_result_read_e2e_test.go) and
[the migration proof](../../test/e2e/migrations_result_read_e2e_test.go).
Both schema engines and both migration phases create a resource whose name is
exactly 63 bytes. The scenarios now retain its actual workload inventory and
require a completed Job and successful owned Pod for every required operation,
carrying the full name, with one exact recorded Apply. The server audit must
receive SQL from that Apply after the result transport recovers; schema controls
add a column while preserving a populated row, and migration controls verify
the three applied revisions and managed rows. An otherwise identical 64-byte
create must fail at the installed name CEL rule and leave no stored resource.
The adverse predicate tests reject empty inventories, truncated labels, wrong
owners, missing operations, unsuccessful Pods, and a second Apply. These
additions reuse the existing scenarios and need execution on the final
identities; local tests supply no runtime pass. Other accepted configuration
boundaries still require their operational evidence.

## Native plan byte and chunk boundaries

`native-plan-size-boundary` in [the data-plane suite](../../test/e2e/plan_size_boundary_e2e_test.go)
generates real SQL inside a credential-free fixture container and publishes it
through the native Ptah CLI. Its publisher has a 256 MiB limit; its operator
task has an explicit 512 MiB limit. This is a separate execution-contract
boundary, not a claim for a larger capacity fleet or a smaller task budget.

Both engines calibrate with three actual operator-produced plans, then require
a saved native file of exactly 8 MiB + 1 byte to reach `invalid_plan_output`.
The runner records the measured file size and configured limit. The refusal
publishes no plan or chunks, dispatches no Apply, and produces only the pinned
diagnostic SQL, attributed to its exact Observe and Plan Pods.

The accepted control is exactly 8 MiB in 16 full 512 KiB immutable chunks.
The suite binds the reconstructed bytes to the native runner result, checks
the exact projected copies, approves that plan and verifies one Apply's SQL
and database effects. PostgreSQL creates one TEXT default; MySQL uses a fixed
100-table VARCHAR set so the pinned parser and database can execute the same
total payload. Every resource name reaches the accepted 63-byte boundary.
Native small [CLI plan readings](../../testdata/e2e/readings/plan-size-small.md)
support the predicate regressions; their standalone Apply does not supply a
cluster-cell pass. Final artifact execution remains required.

## What the SQL evidence must establish

The existing [server audit](../../test/e2e/database_audit_e2e_test.go) counts SQL
received from the exact completed runner Pod's IP. A target-binding or expired
dispatch refusal happens before executor invocation, so the required count is
zero. A positive control must produce records; an empty, truncated or disabled
journal cannot pass. Logs retain the Job and Pod UIDs and safe counters, never
raw credential-bearing SQL.

Drift and history refusals read the database to decide whether the approved
work is still authorized. Their allowed reads cannot be treated as zero SQL.
History inspection can also create an empty revision table. Record the exact
authorized diagnostic/coordination work separately from approved mutation and
verify that no unauthorized statement reached execution. A prefix classifier
that treats every SELECT or WITH statement as harmless is insufficient: either
can invoke mutating work. Database equality alone also misses attempted or
rolled-back mutations.

For a refusal before any Job exists, there is no runner Pod IP to invent. Bind
the server audit to the isolated database/credential and complete watch window;
account for legitimate read Jobs and fail on unidentified traffic. Retain the
fault's admission/persistence time, resource generation, old/new plan identity,
and the allowed control's database effects.

The PostgreSQL migration approval-input scenarios now collect one continuous
statement journal from before the initial resource exists through the replacement
approval gate. Their exact History SQL and parameters are checked against the
pinned Ptah implementation and an actual server reading. Every scoped client must
bind to the migration's Job and terminal Pod; polling retains those identities
across Job TTL cleanup. The harness's database checks have separate exact
loopback-only read permissions. Changed statements or parameters, unknown
clients, non-History runner SQL, failed unauthorized statements and missing
initial History evidence fail the audit. The successful fresh Apply remains the
matching mutation control. See the [reading and source review](../../testdata/e2e/readings/postgresql-migration-history-audit.md).

The MySQL migration scenarios use a fresh database-scoped account for each
approval-input case. Full before/after general-log snapshots retain exact SQL
and expanded parameters, including Prepare and Execute separately. A complete
multiset comparison refuses lost or replaced rows. Every record from that
account or a migration Pod address must belong to an identified History
connection and the exact permitted diagnostic contract. Unknown clients,
changed accounts or selected databases, arbitrary SQL and incomplete sessions
fail. The [actual MySQL reading](../../testdata/e2e/readings/mysql-migration-history-audit.md)
supplies the parser's allowed control; it is not an executed refusal scenario.

This adds refusal-side statement checks for both engines' migration artifact,
apply-policy, transaction-mode and verification-policy edits (AB-02, AB-05,
AB-07 and AB-08). The updated scenarios still need cluster execution.
The schema identity replacement, verification-policy, destructive/exclusion
policy, and artifact/lock-policy/transaction-mode lifecycle rows now check their
distinct Observe/Plan contract. Both schema drift rows now audit the refused
Apply and recovery diagnostics as described below. Both families' executor-image
