# Required evidence for the 0.2.0 profile

This manifest implements the existing PA-01 through PA-12 requirements in
[#242](https://github.com/stokaro/ptah-operator/issues/242). The profile and
limits are in [0.2.0.md](0.2.0.md). Every row below is **Not assessed** until
executed evidence for the qualified commit and runtime bytes supports it.
An issue or source-file link identifies the owner or starting implementation,
not a passing result.

## Functional matrix

Run `make acceptance-coverage` at the candidate commit and retain the output.
It derives the required minors, suites, phase/engine bindings and scenario IDs
from the support catalogs and driver. Run every declared scenario in every
cell; a preparation phase is not coverage. The current catalog has 15 cells
per runtime architecture:

| Suite | Required minors | Phase coverage |
| --- | --- | --- |
| lifecycle | Every minor in `support/kubernetes.json` | upgrade, leader failover, uninstall and reinstall |
| certificates | Every minor in `support/kubernetes.json` | certificate rotation and recovery |
| data-plane | Every minor in `support/kubernetes.json` | admission/authority contract and schema lifecycle on both engines |
| migrations-postgresql | Every minor in `support/kubernetes.json` | PostgreSQL migrations, schema reference data, operational alerting |
| migrations-mysql | Every minor in `support/kubernetes.json` | MySQL migrations and schema reference data |

Execute that matrix on Linux amd64 and arm64. Record architecture with each
job; the current default CI matrix alone does not supply the additional
architecture evidence. Record real database server versions and digests, the
Ptah identity from `support/ptah.json`, chart and runtime digests, effective
values, and controller-state/runner-protocol versions for each environment.
Freeze the generated scenario listing with its hash before executing it.

Q-02 through Q-06 run across the functional matrix. Q-07 runs on every
supported minor and runtime architecture as well as both engines/families;
record each loss/backup case separately. Q-09 uses each minor/architecture's
monitoring stack, with database-specific incident rows exercised for each
engine. Q-10 runs for each minor and runtime architecture; client command
proofs also run on each shipped macOS/Linux client platform. Q-11 covers both
image architectures and all four client OS/architecture combinations in the
release inventory. Q-12 joins the complete set rather than sampling it.

Boundary storage tests do not stand in for runtime limits: the maximum
accepted plan/chunk projection must reach the claimed executable path. The
smaller workload bands in Q-08 describe capacity and do not waive this Q-05
requirement. An absent published predecessor is the explicit first-release
disposition in the profile; synthetic transition and recovery rows still run.

## Evidence record and execution order

Freeze the profile and this manifest first. Prepare the missing tools in the
single qualification branch. Freeze the final implementation and artifact
manifest, then run the expensive workflows sequentially. Their internal matrix
may use its configured concurrency; do not launch another full workflow while
the preceding qualification workflow consumes those slots.

Every report row records the profile/manifest hashes, source commit, chart and
image digests, server/platform identities, fixture/configuration revision,
timestamps, exact CI run/job/attempt or controlled local-run identity,
assertion output and relevant database evidence. Keep failed rows and explain
reruns. A source-equivalent rebuild is different runtime evidence until its
artifact verification and affected tests are complete.

Complete `support/acceptance/0.2.0.json` from those reports and generate the
record with:

```sh
make acceptance-record ACCEPTANCE_PROFILE=support/acceptance/0.2.0.json
```

Store the generated record, coverage listing, raw reports and immutable
artifact manifest in the durable evidence bundle. Verify its download and
checksums. #584 may record acceptance only after every applicable row passes
and the responsible owners record the bounded decision.
