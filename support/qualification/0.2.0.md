# Qualification profile for 0.2.0

This profile fixes the targets for issues #577 and #242 before qualification.
It is not a supported capacity claim or an acceptance decision. The final
source commit, runtime digests, effective values and evidence belong in
`support/acceptance/0.2.0.json`. Until those are bound and PA-01 through PA-12
pass, the decision remains **Not assessed**.

A failed target is a finding. Changing a target requires a new profile revision,
its rationale and new affected runs; a previous failure stays in the record.
The historical `lab-20` reading does not establish any target below. A run must
record this profile's file digest before provisioning its workload.

The scenario manifest is [0.2.0-coverage.md](0.2.0-coverage.md). Its rows include
work that has not been implemented or executed; a declaration is not evidence.
Freeze both documents in a commit before starting a qualification run. Each
run records that commit, the SHA-256 of both files and its effective settings.
Include the SHA-256 of `0.2.0-monitoring.yaml` in the same run manifest.

## Installation contract

The initial profile uses upstream Kubernetes in kind, with the node images and
kind version pinned in `support/kubernetes.json`. It covers Linux amd64 and
arm64. An emulated image build is not runtime evidence for an architecture.
Run the functional matrix on each architecture; measure capacity separately
for each architecture, engine and supported minor. Record host capacity,
virtualization and whether execution is native or emulated with each result.

PostgreSQL 17.x and MySQL 8.4.x LTS use the matrix image digests in the database
support contract. Record the server's actual version and image digest. Use a
dedicated object-owning PostgreSQL login without superuser privileges, and a
MySQL account scoped to one database without global administration or grant
option. Include observation, planning, Apply and no-change verification with
those accounts. Cross-namespace coordination rows use a PtahRealm with an
explicit namespace allowlist and the same database-to-realm mapping on both
resources.

| Setting | Qualification configuration |
| --- | --- |
| Release | One Helm release named `ptah-operator` in dedicated namespace `ptah-system`; no unrelated application workloads there |
| Replicas | Two, with leader election; chart-default requests/limits, captured in the rendered manifest |
| Workload namespaces | `ptah-qualification-a` and `ptah-qualification-b`; five resources of each family in each namespace |
| Admission | Chart webhooks and policies enabled; `applyPolicyGuard.enabled=true`, with only `system:masters` exempt |
| Separation of duties | `approvals.requireDistinctApprover=true`; distinct author and approver identities, and a workload ServiceAccount with no Kubernetes write permissions |
| Apply policies | OnApproval, Always selected only by the installation administrator, and Never refusal; each is exercised on both families |
| Transactions | PostgreSQL `all`, `file` and `none`; MySQL `none`, with refusal proofs for unsupported modes |
| Pod Security | `restricted` enforced, warned and audited in the release and workload namespaces; pin the policy version to the tested Kubernetes minor |
| Quota in each workload namespace | 24 Pods, 512 Jobs, 512 ConfigMaps, 128 Secrets, 2,048 schema plans, 32,768 plan chunks and 2,048 migration plans; test both available and exhausted quota |
| Fixtures | Databases, registry and monitoring live in separate namespaces; record their privileges and capacity separately from operator/workload budgets |
| Network | Enforcing kindnet with the pinned [Pending-Pod resolver correction](kindnet/README.md); apply the documented operator, task and database egress policies, with actual allowed and denied traffic controls |
| Registry | Authenticated HTTPS, namespace-local pull credentials and an explicit trusted CA; signed digest-addressed schema and migration artifacts with verification policy |
| Certificates | Built-in rotation for the baseline; lifecycle rows also cover a supplied serving Secret and guarded recreation of a deleted generated Secret |
| Admission variants | DefaultTolerationSeconds enabled with 300-second values; separate rows cover disabled/custom tolerations, ExtendedResourceToleration, and AlwaysPullImages with matching chart declarations |
| Pod mutation | No injected sidecars; exercise the documented metadata-based opt-out and fail-closed refusal of an unexpected mutation |
| Result delivery | Default durable delivery enabled. Kubelets use the standard `10Mi` log size without an operator override; retain effective configz evidence on every node. The exact 8 MiB plan remains supported after producer Pod/log removal and manager replacement. |
| Execution | `activeDeadlineSeconds: 900`, `connectTimeout: 10s`, `failureRetryInterval: 30s`, `policy.lockTimeout: 30s`; fault rows record explicit shorter deadlines before injection |

The kindnet correction prevents a live init-container Pod from inheriting a
completed Pod's network policy when their IPs match. The frozen background
population retains 1,000 completed Jobs and their Pods; it exposed this defect
in the original CNI. Build the correction from the pinned recipe before a
measured workload, record the resulting image and agent identities, and repeat
allowed and denied traffic controls while an init container uses an IP also
recorded by a retained Pod. Keep the original failed cold-start result. The
correction changes no workload population, network restriction, or time limit.

[#586](https://github.com/stokaro/ptah-operator/issues/586) requires the full
supported payload to work with default kubelet logging, and acknowledged results
to survive Pod/log removal and manager restart. Earlier 64 MiB log-transport runs
do not prove this requirement. Qualify the durable baseline declared above;
retain each earlier run's original transport and runtime identity.

Legacy log delivery retains the manager's 60-second per-stream ceiling, bounded
further by remaining Lease headroom, and the 60-second per-Pod cooldown after
a timeout. The live cancellation assertion allows at most 75 seconds from
the read starting. Durable delivery must progress independently of diagnostic
log reads. In both modes, record persisted dispatch/execution deadlines and actual
outcome/unresolved timestamps; never restart an expired deadline on failover.

Database transport rows include verified TLS with an explicit trusted CA and
the supported isolated-network connection forms. TLS refusal rows use an
untrusted CA or wrong server identity and must execute no unauthorized SQL.
There is no claim for a cloud-specific IAM mechanism, injected service mesh,
another database release line or another Kubernetes distribution. Expanding
those claims requires the corresponding profile and tests, not an inference
from kind. These limits do not exclude any safety requirement of #242.

There is no published predecessor at profile creation. Record that inventory
in the run evidence; published-predecessor upgrade is not applicable for this
first release. Synthetic successor upgrade, interrupted upgrade, downgrade
refusal, reinstall and uninstall remain required. If a predecessor is published
before qualification, revise the upgrade-source inventory before running it.

## Deployment and workload

Use the Kubernetes, Ptah, suite and database catalogs from the tested commit.
The functional matrix covers both resource families, both database engines and
all supported Kubernetes minors. Each shipped architecture needs artifact and
execution evidence. The capacity matrix runs separately on each engine and
minor; a result does not transfer between cells.

| Dimension | Admitted profile and qualification input |
| --- | --- |
| Runtime | Linux; the catalog-pinned executor, manager, runner and chart by digest |
| Test machine | At least 4 dedicated CPU cores and 16 GiB RAM; record actual host capacity once, not once per kind node |
| Cluster | Three control-plane nodes and one worker; two manager replicas at chart defaults; record effective values and every component's resource requests and limits |
| Workload | 10 PtahSchemas and 10 PtahMigrations, evenly split across two workload namespaces |
| Coordination | One database and independent coordination realm per resource; 20 realms total |
| Refresh | Every resource at a 2-minute interval |
| Concurrency | At most one active operation per resource; at most 20 workload operation Pods running concurrently |
| Schemas and plans | Exercise executable plans in the 3-4 KiB, 240-256 KiB and 960 KiB-1 MiB bands; include retained and projected copies |
| Artifacts | Up to 8 MiB unpacked content per artifact; record compressed and unpacked bytes and manifest digest |
| Migration history | Exercise lengths 2, 32 and 128; mix already-applied and pending versions |
| Database contents | 10,000 deterministic rows per resource, with row digests and schema/history inventories before and after each mutating scenario |
| Input changes | One simultaneous artifact-update batch affecting 5 resources of each family per 10 minutes, plus the resource replacements declared below |
| Approval backlog | In a separate scenario, put 5 resources of each family from the same 20-resource fleet into OnApproval; keep their plans and approvals, then approve that batch |
| Unrelated objects | 1,000 ConfigMaps of 1 KiB and 1,000 completed Jobs spread over two separate namespaces; exclude them from workload counts, include their effect on the manager and API server |
| Churn | During the soak, replace two idle, converged resources of each family every 10 minutes; preserve their databases and use their current desired artifacts |

The application workload uses the documented author and approver identities.
Installation and maintenance use their declared privileges. Admission must
remain enabled throughout capacity and recovery tests. Record enforced network
policies and Pod Security Admission settings; neither a manifest nor a dry run
establishes enforcement.

## Operating targets

The following maxima apply to steady load, the approval backlog and churn,
except where a row names a fault window. Sample every 5 seconds. Retain raw
readings, timestamps, object UIDs and per-process/per-API-server identities.
A missing, reset or mixed-identity counter cannot establish a bound. Report
missing readings explicitly and fail the affected measurement.

| Measurement | Target |
| --- | --- |
| Cold start or changed batch to database-verified convergence | At most 5 minutes from the first submitted eligible write; approval-gated work starts at admission of the first required approval in the batch |
| Oldest database observation | At most 5 minutes for every eligible resource |
| Reconciliation overdue | At most 60 seconds for every eligible resource |
| Completed operation latency | p95 at most 60 seconds; every attempt completed or visibly unresolved within its configured execution and collection deadlines |
| Queue delay | p95 at most 30 seconds; no eligible resource goes 5 minutes without progress |
| Manager RSS | At most 192 MiB per process, with zero OOM kills or unplanned restarts |
| Manager CPU | At most 1 core averaged over each measured scenario, summed across replicas |
| API pressure | Zero client HTTP 429 responses and zero API priority/fairness rejections attributable to the workload; at most 10 seconds of aggregate client throttling per 10-minute window |
| API demand | At most 100 requests/second, averaged over each 60-second window and summed across manager identities; record workload, monitoring and fixture traffic separately |
| Admission latency | p95 at most 1 second for operator webhooks, measured separately on every API server |
| Pods | At most 20 running workload operation Pods and 20 pending workload operation Pods; record both maxima |
| Retained plan payloads | At most 128 MiB after each maintenance checkpoint; every active, applied, approved or unresolved pin still resolves to its exact bytes |
| Registry recovery | Fresh database-verified convergence within 3 minutes of removing a demonstrated 3-minute registry outage |
| All-manager replacement | Fresh database-verified convergence within 3 minutes; an approval admitted within 90 seconds and its Apply dispatched within 3 minutes |
| Hung result collection | Collection cancellation within 75 seconds; unrelated eligible work converges within 180 seconds; the original claim and unresolved evidence remain accounted for |

Run a 90-minute soak after cold-start convergence. This spans 45 declared
refresh intervals and nine input-change/retention checkpoints. Record actual
completed cycles per resource; wall-clock duration alone is insufficient.
Require at least 30 complete read-only refresh cycles per logical workload
slot, all nine churn/checkpoint rounds, and no unexplained growth, starvation or safety
violation. Compare post-maintenance inventory and manager RSS at equivalent
quiescent checkpoints. Across the final three checkpoints, retained payload
bytes must not grow and per-process RSS must stay within 10% of the first of
those three checkpoints as well as its absolute limit.

A slot's churn record lists every old/new resource UID and its lifetime. Count
only completed cycles from those lifetimes, without carrying an old object's
status into its replacement. Every incarnation present for at least two
refresh intervals must complete a cycle. This measures progress despite
replacement without asking a ten-minute-old resource for ninety minutes of
history.

Compute percentiles from at least 20 actual observations in the declared
scenario/population, using the recorded histogram or individual durations.
Report the sample count and boundaries with every percentile. A smaller
population cannot pass that percentile target. Measure human approval waiting
separately; deliberate faults and overload have their own time windows and
recovery targets rather than being blended into steady-state latency.

At each checkpoint, export obsolete evidence with its digests, wait for a
quiescent maintenance window, re-read every pin listed in the operations
runbook, and delete only unpinned plans with UID preconditions. Resume normal
work and prove convergence after maintenance. No automatic retention behavior
is assumed.

In a separate retention fault scenario, use the same 20-resource fleet with
one pending schema approval and one unresolved migration Apply. Preserve
their plans, payloads and run evidence through pruning and garbage collection;
verify their identities and bytes before and after it. The soak cycle-count
requirement applies to the eligible fleet during the soak, not to these
intentionally blocked resources in the separate fault scenario.

Run separate overload probes at 40 resources and with a plan larger than
8 MiB. The plan must reach the documented size refusal. At excess concurrency,
record queueing, refusals and resource pressure; no unauthorized SQL, replay,
loss of unresolved evidence, silent dropped work or manager OOM is permitted.
After returning to 20 resources, eligible work must recover within 5 minutes.
These probes establish behavior outside the profile, not a larger admitted
capacity. Slow-dependency probes must include both registry loss and a database
response delay of 30 seconds.

## Alert targets

Use 5-second Prometheus scrapes and evaluations, a 5-second Alertmanager group
wait, and a receiver that records both firing and resolved notifications.
Scrape every manager Pod and each API server directly with its proper TLS and
authorization settings. Include installation identity in external labels;
resource drill-down follows the runbook without adding resource names to the
metric label set.

The values in `0.2.0-monitoring.yaml` enable the chart's rules. They are
qualification settings, not chart defaults. The certificate warning below is
24 hours before expiry; the existing accelerated 60-second warning proof is
supporting evidence and does not replace a run with these values.

| Incident / alert | Threshold and start event | Receiver deadline | Resolution deadline |
| --- | --- | --- | --- |
| Unresolved Apply | First persisted unresolved Apply record | 45 seconds after persistence | 45 seconds after verified recovery clears the record |
| Unresolved view unavailable / all managers lost / leader scrape lost | 60 seconds of continuous unsynchronized or absent view | 105 seconds after the first failed scrape or view transition | 45 seconds after a synchronized leader is scraped |
| Unresolved view read failures | First failed state read in a 60-second window | 45 seconds after the failure | 105 seconds after the last failure |
| Resource overdue | More than 60 seconds after its persisted next reconciliation deadline | 105 seconds after that deadline | 45 seconds after the overdue condition clears |
| Operation stalled | More than 60 seconds from the persisted operation claim | 105 seconds after the claim | 105 seconds after the operation leaves flight |
| Lock release owed | An owed release persists for 60 seconds | 105 seconds after it became owed | 45 seconds after the release completes |
| Certificate expiring | Signed certificate NotAfter minus 24 hours | 45 seconds after the signed threshold | 45 seconds after every serving endpoint and scrape shows the renewed certificate |
| Plan store large | Retained schema payload exceeds 128 MiB | 45 seconds after the measured crossing | 45 seconds after safe pruning brings it below the threshold |
| Operations failing | More than three failures for one family/stage in five minutes | 45 seconds after the fourth failure | 345 seconds after the last failure |
| Admission unavailable | First real calling-webhook error in five minutes | 45 seconds after the API server records the rejection | 345 seconds after the last rejection |
| Upgrade failed | Upgrade hook Job reaches Failed, or the 15-minute upgrade deadline expires without success | 45 seconds after that event | 45 seconds after the documented retry establishes a healthy release |

The upgrade signal and receiver route must be implemented and tested under #581;
the chart does not currently supply that rule. Measure observation delay from
the underlying event, not from the poll that notices it. Where a rolling window
keeps a recovered event visible, retain the last event timestamp and the
whole resolution interval. A pending approval or ordinary policy refusal must
produce no failure notification during a ten-minute negative-control window;
its normal observation/retry cadence continues. No separate approval-age paging
policy is enabled in this profile.

## Recovery objectives

Operator-state and database backups each have an RPO of **5 minutes**. The
operator-state-only loss drill has an RTO of **15 minutes** with the database
still available. The database and combined-loss drill has an RTO of
**30 minutes** through complete application service restoration. Start the clock at the injected loss, including
isolation, cluster provisioning, restore, manual diagnosis and verification.
Stop only after the database, operator state, admission and a representative
approved change have passed their recovery assertions.

Create the backup under the documented access controls and ordering. Record
backup start/completion times, exact object UIDs, artifact identities, plan
payload digests, preserved execution evidence and the database recovery point.
Restore into a separate cluster and database instance. Exercise an idle backup,
loss during Apply, and a backup lagging the database by 5 minutes. Reconcile
expected schema, managed-row and migration-history inventories against each
recovery point. An old approval must not authorize replay, and an uncertain
Apply must remain visible until its documented recovery action accounts for it.

A missed RTO/RPO fails this profile. Successful process startup, restored CRs,
or a green readiness probe alone cannot end the recovery clock.

## Evidence and decision

| Responsibility | Accountable role and required handoff |
| --- | --- |
| Engineering | The repository release maintainer owns the source/artifact manifest, fixes, proof coverage and final technical decision |
| Operations | The target installation owner owns effective values, receiver/incident routing, backups, restore access and the deployment decision |
| Evidence storage | The repository release maintainer owns the durable evidence bundle; the installation owner owns restricted backups and credential-bearing drill evidence |

Record the named person and contact for each role in the final acceptance
record before a production decision. This profile assigns responsibilities;
it does not assert that a person approved an unexecuted result.

### Evidence access

The release maintainer publishes only reviewed, sanitized evidence in the
public bundle: identities, checksums, assertions, aggregate measurements and
the disposable fixture's expected database contents. Public read access does
not grant permission to replace the bundle. Publication uses the repository's
release permissions and immutable artifacts; controlled staging remains
separate from an official release.

The installation owner keeps database backups, Secret exports, private keys,
kubeconfigs and unsanitized logs in a separate encrypted store. Access is
limited to the named restore operators and engineering reviewers who need
those contents. Record the access grants, encryption/key references and access
audit location in the restricted evidence inventory; never include credentials
or decryption material in the public bundle or command arguments. Encrypt
transfers and retained copies. Local working directories use mode 0700 and
credential-bearing files mode 0600.

Before counting a retained bundle as available, verify its hashes and an
authorized download. For the restricted bundle, also prove an unauthorized
reader is refused and the designated restore operator can decrypt and read
the backup. Retain the required keys and access for the same horizon as the
evidence. Remove plaintext working copies and drill credentials after those
checks and the restore drill; record the cleanup without exposing their
contents. #579 executes the backup/access proof and #584 verifies the final
storage locations and handoff.

Keep every successful and failed run's job ID, attempt, source commit, runtime
and profile digests, raw bounded measurements and assertion results. Preserve
the bundle for at least 12 months after the 0.2.0 release and through any longer
support or recovery horizon declared at release. An expiring Actions artifact
alone is insufficient; verify a durable copy and its checksums.

The acceptance record must separately state which measurements meet these
targets and which PA requirements remain unassessed. No exclusion is declared
for a PA requirement by this profile. Engineering and operations must name the responsible owners
and record the final decision and deployment handoff after the evidence exists.

Reassess affected evidence after any runtime-byte, API/state, policy, platform,
privilege, topology, capacity or recovery-procedure change. Review security
advisories at least weekly and immediately when an applicable advisory is
reported. A blocking safety or exploitable-security finding revokes acceptance
for the affected profile until it is resolved and verified.
