# 0.2.0 recovery evidence

Issue [#579](https://github.com/stokaro/ptah-operator/issues/579) requires actual
restores of both database and operator state. The database prerequisite,
operator-assisted database-loss pilots, namespace rebuilds and cold-cluster
pilots below have run on development images. Their results do not complete
PA-07 or establish recovery under the final installation profile. The [frozen profile](0.2.0.md#recovery-objectives) still sets the recovery
targets and the [coverage manifest](0.2.0-coverage.md) still defines the scope.

## Backup inventory

Keep the original backup immutable. Record a digest, start and completion time,
recovery point, access policy, encryption key reference, retention period, and
restore command for each entry. Credentials and private payloads belong in the
restricted store; the public record contains their identities and checksums.

| State | Required contents | Recovery assertion |
| --- | --- | --- |
| Kubernetes API contracts | All nine CRDs, stored versions and contract counters | The selected release can read every restored object; admission enforces the restored contract |
| Custom resources | Specs, status, metadata, original UIDs, execution bindings, plan references, approval stamps, acknowledgments, and the unresolved-run annotation | Every original operation, plan and decision remains identifiable; a rebuild records old-to-new UID mappings without rewriting old authorization |
| Plan payloads | Every `PtahSchemaPlanChunk`, original UID and content digest; referenced immutable migration artifacts | Restored bytes match their digests; a rebuilt chunk cannot satisfy an old UID reference |
| Execution evidence | Exact Job and Pod identities, operation claims, deadlines, result transport, pending observations, unresolved runs, database session identities, and coordination Lease records | Account for surviving execution before replacement; archived Leases are evidence, not permission to recreate a stale holder |
| Release and admission | Chart and image identities, stored Helm manifests and hooks, effective values, admission singleton, RBAC, policies and bindings, webhook configuration, and certificate state | Installed authority matches the recorded release; no partially restored controller can dispatch work |
| Dependencies and access | Database and registry Secrets, policy ConfigMaps, trust roots, `PtahRealm` grants, artifact digests, and their original identities | Recovery actors can read the backup and dependencies; unauthorized actors cannot; required artifacts remain retrievable |
| Database | Schema, managed rows, actual Ptah revision history, users, roles, grants and ownership | Restored state matches the declared database recovery point, with expected and observed loss recorded separately |

A database dump and a Kubernetes export are separate recovery points. Do not
label them consistent because their commands ran near each other. Record what
could change between them. The idle case must establish quiescence; the
in-flight and lag cases must retain and account for the resulting uncertainty.
An object export that creates new UIDs is a rebuild, not a control-plane
snapshot that preserves them.

Stopping a manager does not stop its existing Apply Jobs. Losing API access
does not stop a Pod or its open database session. Before enabling replacement
execution, prove that the old executor has stopped or that a database fence
blocks both existing sessions and new connections. Keep the evidence needed
to diagnose its outcome. A restored resource with automatic application still
has that policy: controlled rebuilds use suspension and `OnApproval` until the
old work is accounted for.

## Executable database prerequisite

Run from the repository root with Python 3, Docker CLI, `age` and `age-keygen`
installed. The procedure explicitly uses `remote-dev-container`; it creates
only uniquely named, labeled test containers, volumes and an internal network.
It publishes no host ports and removes its own Docker resources on exit. The
pinned PostgreSQL 17 and MySQL 8.4 images are retained for reuse.

```sh
python3 support/qualification/probes/database_restore.py postgresql /tmp/ptah-restore-postgresql
python3 support/qualification/probes/database_restore.py mysql /tmp/ptah-restore-mysql
```

Each output directory must be new. Run the engines sequentially. The directory
uses mode 0700 and its files use mode 0600. It contains `result.json`, encrypted
fixture backups, a private restore identity and private diagnostics. Never
publish that directory. The result records the procedure hash, pinned image,
actual image identity, source commit, step timestamps, comparison hashes,
individual assertions and cleanup outcome. A run is successful only when the
process exits zero, every assertion passes and cleanup succeeds.

The [September 30 preflight record](evidence/db-restore-preflight-2026-09-30.json)
contains the successful PostgreSQL and MySQL assertions and the failed MySQL
bootstrap attempt. Both successful runs used the recorded procedure hash;
their Docker containers, volumes and networks were removed. The private
archives still need the durable storage and key-custody handoff described below.

The procedure creates a database with a primary key, two populated rows and a
read-only account. It compares schema, data and access inventories, takes an
actual backup, encrypts it, verifies a wrong-key refusal and decrypts it with
the intended key. It then commits one additional row, deletes the source
container **and its volume**, and provisions a fresh target. The target must
initially have neither the database nor the reader account. Restoration must
recover the original rows and permissions, lose exactly the declared later
row, admit the restored reader's SELECT, refuse that reader's DDL for a
permission reason, and admit a new administrator change.

PostgreSQL uses `pg_dumpall --roles-only` followed by `pg_dump -Fc`. The fresh
target has a separate bootstrap administrator, so restoring the original roles
does not collide with that bootstrap identity. Roles are restored first, then
`pg_restore --exit-on-error --create`; ownership and grants are preserved.
The extra recovery administrator is a declared fixture identity, not an
assertion that every cluster-level role is identical.

MySQL uses `mysqldump --all-databases --single-transaction --routines --events
--triggers --flush-privileges --set-gtid-purged=OFF` against the same pinned
version at both ends. This includes grant tables and reloads their privileges.
The fixture changes no DDL or grants during backup. The manual warns that
concurrent DDL is incompatible with the consistency assumption of
[`--single-transaction`](https://dev.mysql.com/doc/refman/8.4/en/mysqldump.html).
That procedure has not established an in-flight DDL backup strategy.

The first MySQL execution failed during initialization because `MYSQL_PWD` was
set in the server environment before the entrypoint configured root's
password. The procedure now supplies it only to client commands through a
private environment file. The failed run remains failed; its resources were
removed before the corrected run.

The procedure removes the disposable database credential files. The retained
age identity is still sensitive recovery material. Move it and the encrypted
archives to the designated restricted evidence store before relying on their
availability; prove authorized download, unauthorized-access refusal and key
retention there. Local wrong-key rejection proves encryption behavior only.

The recorded database recovery duration starts before source destruction and
includes new-instance provisioning, decryption, restoration and validation. It
is **not the profile's RTO**: it omits operator restoration, admission, manual
diagnosis and an operator-approved change. The fixture contains no Ptah
revision history. It proves no operator, migration, surviving-Apply, five-minute
lag, production-store, final-artifact or full-matrix result.

## Operator-assisted database-loss pilots

`probes/operator_restore.py` supports idle recovery for each engine and resource
family. Its default loss type is `database`. It uses a real operator, real OCI artifacts,
plan-bound approvals and, for migrations, the actual Ptah history table.
For `--loss database`, the original database container and volume are destroyed.
The operator's Kubernetes state survives; its encrypted checkpoint is evidence,
not a restored control-plane backup.

`--loss operator` deletes the entire fixture namespace and restores dependencies
and the resource from the decrypted backup. `--loss combined` also destroys and
restores the database and its volume. These modes use the documented controlled
rebuild: original plans, chunks, approvals and workload evidence remain archived
under their original identities; the API assigns new UIDs to the rebuilt
resource and dependencies. No old approval is rewritten to bind a new UID.
The restored resource starts suspended with `OnApproval`, then obtains a fresh
execution binding and plan. Both the original approval's missing plan and the
old resource UID against the new plan must be refused before fresh authorization.
The full watch retains both resource UIDs, so deletion cannot erase an old
executor from the no-replay check.

The installed release and CRDs are outside this namespace loss. The backup
records all nine CRD specifications and both admission webhook configurations;
the procedure compares their original identities and contracts after rebuild.
These modes do not rehearse loss of the complete Kubernetes control plane.
The frozen profile requires restoration into a separate cluster and includes
cluster provisioning in its recovery clock. Same-cluster namespace pilots do
not satisfy that requirement, even when their measured durations fit the
numeric bounds. Their native results must be recorded separately from the
database-only pilots below. Operator-only recovery permits no database loss and has the fifteen-minute
bound; combined loss has the thirty-minute bound. Both use the five-minute RPO.

The [namespace and combined-loss pilot record](evidence/namespace-restore-pilots-2026-09-30.json)
retains eight completed runs on operator commit `4560860c`. All 364 assertions
passed, including new UID mappings and exact expected data loss. The original
cluster, fixture containers, task image references, claim volumes and API tunnel
were removed after collection. These results cover same-cluster rebuilds only.
The temporary registries were removed too; their historical references are not
a portable recovery kit. Final-artifact availability and durable custody remain
required before acceptance.

Before backup, the resource is suspended and its exact Apply Pod must have
stopped. The procedure records continuous Job and Pod watches from listed
resource versions, with exact start and end sentinels. Ownership, runner
commands and immutable execution specifications must agree. Missing Apply
Pods, replacement Pods, watch errors and interrupted watches fail the proof.
After restoration, the procedure compares schema, rows, permissions and
migration history, observes reconciliation, rejects an old-plan approval,
and requires one fresh approval to produce one new Apply and a database change.
It records the actual lost row and preserves original and fresh identities.

Run the predicate controls first. They include real workload readings, stale
status, misleading labels, missing ownership and replacement-Pod controls:

```sh
python3 -m unittest discover -s support/qualification/probes -p '*_test.py' -v
```

The native procedure also requires the regular e2e prerequisites, `kubectl`,
Python 3 and `age`. Run the following from a clean, committed checkout in one
shell so the bootstrap's API tunnel stays available. Use a new output directory
and run cases sequentially; the cluster is shared only by these disposable cases.

```sh
proof_dir=$(mktemp -d /tmp/ptah-operator-restore.XXXXXX)
chmod 700 "$proof_dir"
export DOCKER_CONTEXT=remote-dev-container
export K8S_VERSION=1.37.0
export E2E_RUN_ID=020-operator-restore
export E2E_STOP_AFTER=bootstrap
export E2E_ENVIRONMENT_FILE="$proof_dir/environment"
export E2E_TIMING_LEDGER="$proof_dir/timings.jsonl"
export E2E_TIMING_CONTEXT="$proof_dir/context.json"
cleanup() { LAB_ENVIRONMENT="$E2E_ENVIRONMENT_FILE" demo/bin/lab down; }
trap cleanup EXIT
make e2e || exit "$?"
for engine in postgresql mysql; do
  for family in schema migration; do
    python3 support/qualification/probes/operator_restore.py \
      "$engine" "$family" "$E2E_ENVIRONMENT_FILE" \
      "$proof_dir/$engine-$family" || exit "$?"
  done
done
```

The [September 30 pilot record](evidence/operator-db-restore-pilots-2026-09-30.json)
retains all four final-procedure results on operator commit `5843171f` and the
failed attempts that preceded them. The task cluster, registry, external fixture,
created image tags, claim and API tunnel were removed; no owned recovery
containers, volumes or networks remained. The final runs passed 154 assertions:

| Engine | Family | Recovery seconds | RPO upper bound, seconds |
| --- | --- | --- | --- |
| postgresql | schema | 90.502 | 4.317 |
| postgresql | migration | 71.853 | 4.374 |
| mysql | schema | 92.716 | 3.611 |
| mysql | migration | 77.62 | 3.667 |

Each run records the operator revision, operator and executor image digests,
procedure and helper hashes, actual backup hashes, per-assertion results and
cleanup outcome. It requires RPO at most five minutes and recovery at most
thirty minutes. The recovery clock starts before source destruction and ends
after the fresh approved database change and workload accounting. The RPO
upper bound uses backup start, which precedes its database snapshot. These are
measurements of this idle fixture; no manual diagnosis or uncertain-run
acknowledgment is needed in this case.

The early pilot attempts exposed procedure defects: an expired API tunnel,
an incorrect suspended-condition predicate and an unsupported watch CLI flag.
Their failed or interrupted results remain distinct from successful runs.
The watch now uses the raw Kubernetes API from an exact resource version, and
readiness must belong to the current generation. The private output directories
must remain restricted and follow the same archive and key-custody handoff as
the database prerequisite.

## Cold-cluster recovery procedure

`probes/cluster_restore.py` extends the idle procedure for `--loss operator`
and `--loss combined`. It destroys the disposable source kind cluster, provisions
a separate cluster after loss, and restores namespace state from the encrypted
backup there. Its clock includes provisioning, release installation, database
restoration where required, admission checks and the fresh approved change.
The external fixture registry survives until the proof ends. Both clusters and
all task databases are removed afterward.

Run one case per freshly bootstrapped source cluster, from the same clean commit
used to build it. In the bootstrap shell above, replace the engine/family loop
with this command:

```sh
python3 support/qualification/probes/cluster_restore.py \
  postgresql schema "$E2E_ENVIRONMENT_FILE" "$proof_dir/cold-postgresql-schema" \
  --loss operator
```

The source API node names must match the exact Docker cluster being destroyed.
The replacement must have a new control-plane UID and the same operator revision,
Ptah revision, Kubernetes version and platform. The backup includes the installed
Helm release's effective values, manifests and hooks. The replacement release is
archived separately. CRD schemas and webhook rules must remain equal after
accounting for new UIDs, installation service addresses and generated CAs.
The replacement's registry pull credential is a declared additional Secret;
original backup Secrets are restored unchanged.

The [September 30 cold-cluster pilot](evidence/cold-cluster-restore-pilot-2026-09-30.json)
ran PostgreSQL/PtahSchema operator-state loss on commit `1ad45b48`. The original
cluster was destroyed, the replacement received new control-plane and resource
identities, old approvals were refused, and one fresh approved change reached
the retained database. All 55 assertions passed. Recovery took 441.773 seconds,
including replacement provisioning, against the 900-second operator-only bound;
the conservative backup-age bound was 12.440 seconds. Both task clusters, their
database resources, 26 created image references and both API tunnels were removed.

The [MySQL/PtahMigration combined-loss pilot](evidence/cold-cluster-mysql-migration-pilot-2026-09-30.json)
ran on commit `77ca3bcf`. It destroyed the source cluster and database volume,
restored MySQL 8.4.11 and its actual Ptah history, and rebuilt operator state in
a new cluster. All 56 assertions passed. Recovery took 440.211 seconds against
the 1,800-second combined-loss bound, with an RPO upper bound of 8.410 seconds.
Only the declared post-backup row was lost. Old authorization was refused and
one fresh approved migration reached the restored database. Archive checksums,
replacement node identities, native database identity and cleanup were checked
independently; both clusters, task database resources, 26 created image references
and both API tunnels were removed.

These are development pilots. Their shared amd64 host has less than the frozen
16 GiB memory minimum, and their bootstrap does not establish the final installation
profile. The remaining engine/family/loss combinations, in-flight and lag cases, final
runtime artifacts, durable dependency availability and owner acceptance remain
outstanding. The namespace pilots above supply no cold-cluster RTO result.

## Required operator recovery matrix

The complete matrix remains 36 cells: each of PostgreSQL and MySQL, each of
`PtahSchema` and `PtahMigration`, each loss type below, and each timing case.

| Loss type | Actual loss and restoration |
| --- | --- |
| Operator state only | Remove the declared operator state, retain the database, restore the recorded control-plane backup or perform the declared rebuild |
| Database only | Remove the database instance and its storage, retain operator state, restore the database backup into a new isolated instance |
| Combined | Remove both declared components and restore both backups in the recorded order |

| Timing | Required observations |
| --- | --- |
| Idle | Back up a quiescent state; compare restored schema, rows, history and execution evidence |
| During Apply | Inject loss while the exact approved operation is running; account for surviving execution, preserve uncertain evidence, and refuse overlap and old-approval replay |
| Operator backup five minutes behind the database | Record both recovery points and the intervening commits; restore the older operator state without replaying work already reflected in the database |

For every cell, retain original and restored identities, actual backup
checksums, the fence and its verification, expected versus observed data loss,
the diagnosis or acknowledgment, fresh authorization, and the resulting
database effects. Start the profile clock at injected loss. End it only after
database state, operator state, admission and a representative approved change
have passed. The RPO remains five minutes; RTO remains fifteen minutes for
operator-only loss and thirty minutes for database or combined loss.

No cell is accepted by the database prerequisite. Execution on the final
runtime identities, the complete operator procedure, durable evidence and the
owner handoff remain required by #579, #583 and #584.
