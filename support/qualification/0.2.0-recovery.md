# 0.2.0 recovery evidence

Issue [#579](https://github.com/stokaro/ptah-operator/issues/579) requires actual
restores of both database and operator state. The database procedure below is
an executed prerequisite. It does not qualify operator recovery or complete
PA-07. The [frozen profile](0.2.0.md#recovery-objectives) still sets the recovery
targets and the [coverage manifest](0.2.0-coverage.md) still defines the scope.

## Backup inventory

Keep the original backup immutable. Record a digest, start and completion time,
recovery point, access policy, encryption key reference, retention period, and
restore command for each entry. Credentials and private payloads belong in the
restricted store; the public record contains their identities and checksums.

| State | Required contents | Recovery assertion |
| --- | --- | --- |
| Kubernetes API contracts | All nine CRDs, stored versions and contract counters | The selected release can read every restored object; admission enforces the restored contract |
| Custom resources | Specs, status, metadata, original UIDs, execution bindings, plan references, approval stamps, acknowledgments, and the unresolved-run annotation | Every original operation, plan and decision remains identifiable; a rebuild records old-to-new UID mappings without rewriting old authorization |
| Plan payloads | Every `PtahSchemaPlanChunk`, original UID and content digest; referenced immutable migration artifacts | Restored bytes match their digests; a rebuilt chunk cannot satisfy an old UID reference |
| Execution evidence | Exact Job and Pod identities, operation claims, deadlines, result transport, pending observations, unresolved runs, database session identities, and coordination Lease records | Account for surviving execution before replacement; archived Leases are evidence, not permission to recreate a stale holder |
| Release and admission | Chart and image identities, stored Helm manifests and hooks, effective values, admission singleton, RBAC, policies and bindings, webhook configuration, and certificate state | Installed authority matches the recorded release; no partially restored controller can dispatch work |
| Dependencies and access | Database and registry Secrets, policy ConfigMaps, trust roots, `PtahRealm` grants, artifact digests, and their original identities | Recovery actors can read the backup and dependencies; unauthorized actors cannot; required artifacts remain retrievable |
| Database | Schema, managed rows, actual Ptah revision history, users, roles, grants and ownership | Restored state matches the declared database recovery point, with expected and observed loss recorded separately |

A database dump and a Kubernetes export are separate recovery points. Do not
label them consistent because their commands ran near each other. Record what
could change between them. The idle case must establish quiescence; the
in-flight and lag cases must retain and account for the resulting uncertainty.
An object export that creates new UIDs is a rebuild, not a control-plane
snapshot that preserves them.

Stopping a manager does not stop its existing Apply Jobs. Losing API access
does not stop a Pod or its open database session. Before enabling replacement
execution, prove that the old executor has stopped or that a database fence
blocks both existing sessions and new connections. Keep the evidence needed
to diagnose its outcome. A restored resource with automatic application still
has that policy: controlled rebuilds use suspension and `OnApproval` until the
old work is accounted for.

## Executable database prerequisite

Run from the repository root with Python 3, Docker CLI, `age` and `age-keygen`
installed. The procedure explicitly uses `remote-dev-container`; it creates
only uniquely named, labeled test containers, volumes and an internal network.
It publishes no host ports and removes its own Docker resources on exit. The
pinned PostgreSQL 17 and MySQL 8.4 images are retained for reuse.

```sh
python3 support/qualification/probes/database_restore.py postgresql /tmp/ptah-restore-postgresql
python3 support/qualification/probes/database_restore.py mysql /tmp/ptah-restore-mysql
```

Each output directory must be new. Run the engines sequentially. The directory
uses mode 0700 and its files use mode 0600. It contains `result.json`, encrypted
fixture backups, a private restore identity and private diagnostics. Never
publish that directory. The result records the procedure hash, pinned image,
actual image identity, source commit, step timestamps, comparison hashes,
individual assertions and cleanup outcome. A run is successful only when the
process exits zero, every assertion passes and cleanup succeeds.

The [September 30 preflight record](evidence/db-restore-preflight-2026-09-30.json)
contains the successful PostgreSQL and MySQL assertions and the failed MySQL
bootstrap attempt. Both successful runs used the recorded procedure hash;
their Docker containers, volumes and networks were removed. The private
archives still need the durable storage and key-custody handoff described below.

The procedure creates a database with a primary key, two populated rows and a
read-only account. It compares schema, data and access inventories, takes an
actual backup, encrypts it, verifies a wrong-key refusal and decrypts it with
the intended key. It then commits one additional row, deletes the source
container **and its volume**, and provisions a fresh target. The target must
initially have neither the database nor the reader account. Restoration must
recover the original rows and permissions, lose exactly the declared later
row, admit the restored reader's SELECT, refuse that reader's DDL for a
permission reason, and admit a new administrator change.

PostgreSQL uses `pg_dumpall --roles-only` followed by `pg_dump -Fc`. The fresh
target has a separate bootstrap administrator, so restoring the original roles
does not collide with that bootstrap identity. Roles are restored first, then
`pg_restore --exit-on-error --create`; ownership and grants are preserved.
The extra recovery administrator is a declared fixture identity, not an
assertion that every cluster-level role is identical.

MySQL uses `mysqldump --all-databases --single-transaction --routines --events
--triggers --flush-privileges --set-gtid-purged=OFF` against the same pinned
version at both ends. This includes grant tables and reloads their privileges.
The fixture changes no DDL or grants during backup. The manual warns that
concurrent DDL is incompatible with the consistency assumption of
[`--single-transaction`](https://dev.mysql.com/doc/refman/8.4/en/mysqldump.html).
That procedure has not established an in-flight DDL backup strategy.

The first MySQL execution failed during initialization because `MYSQL_PWD` was
set in the server environment before the entrypoint configured root's
password. The procedure now supplies it only to client commands through a
private environment file. The failed run remains failed; its resources were
removed before the corrected run.

The procedure removes the disposable database credential files. The retained
age identity is still sensitive recovery material. Move it and the encrypted
archives to the designated restricted evidence store before relying on their
availability; prove authorized download, unauthorized-access refusal and key
retention there. Local wrong-key rejection proves encryption behavior only.

The recorded database recovery duration starts before source destruction and
includes new-instance provisioning, decryption, restoration and validation. It
is **not the profile's RTO**: it omits operator restoration, admission, manual
diagnosis and an operator-approved change. The fixture contains no Ptah
revision history. It proves no operator, migration, surviving-Apply, five-minute
lag, production-store, final-artifact or full-matrix result.

## Required operator recovery matrix

The complete matrix remains 36 cells: each of PostgreSQL and MySQL, each of
`PtahSchema` and `PtahMigration`, each loss type below, and each timing case.

| Loss type | Actual loss and restoration |
| --- | --- |
| Operator state only | Remove the declared operator state, retain the database, restore the recorded control-plane backup or perform the declared rebuild |
| Database only | Remove the database instance and its storage, retain operator state, restore the database backup into a new isolated instance |
| Combined | Remove both declared components and restore both backups in the recorded order |

| Timing | Required observations |
| --- | --- |
| Idle | Back up a quiescent state; compare restored schema, rows, history and execution evidence |
| During Apply | Inject loss while the exact approved operation is running; account for surviving execution, preserve uncertain evidence, and refuse overlap and old-approval replay |
| Operator backup five minutes behind the database | Record both recovery points and the intervening commits; restore the older operator state without replaying work already reflected in the database |

For every cell, retain original and restored identities, actual backup
checksums, the fence and its verification, expected versus observed data loss,
the diagnosis or acknowledgment, fresh authorization, and the resulting
database effects. Start the profile clock at injected loss. End it only after
database state, operator state, admission and a representative approved change
have passed. The RPO remains five minutes; RTO remains fifteen minutes for
operator-only loss and thirty minutes for database or combined loss.

No cell is accepted by the database prerequisite. Execution on the final
runtime identities, the complete operator procedure, durable evidence and the
owner handoff remain required by #579, #583 and #584.
