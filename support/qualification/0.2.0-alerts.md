# Alert proof inventory for 0.2.0

This inventory implements Q-09 and #581. Every row remains **Not assessed**
until its live fault, receiver delivery, recovery, and resolution pass on the
qualified identities. The [frozen profile](0.2.0.md#alert-targets) supplies each
row's threshold, start event, delivery deadline, and resolution deadline.
The [monitoring values](0.2.0-monitoring.yaml) supply the chart settings.

Run every row on each supported Kubernetes minor and runtime architecture.
Run database-specific faults on both engines and family-labeled faults on both
families. Installation-wide signals have no family label; plan storage counts
schema payloads because migration plans carry no SQL payload. Record those
dispositions explicitly.

The receiver is the alerting phase's `alert-sink`. Record its actual firing and
resolved payloads, installation labels, bounded family/operation/stage labels,
severity, runbook URL, and timestamps. Metric labels must not acquire resource,
Job, Pod, plan, or execution IDs. Keep those identities in the evidence and
runbook drill-down instead.

## Certificate proof preparation

The warning fixture expires 24 hours plus five minutes after it is signed.
Its threshold therefore crosses after five minutes while admission remains
valid. A second leaf, signed under the same installed CA and serving key with
the same DNS identities, then expires after five minutes for the separate
admission fault. This avoids substituting a shorter warning threshold.

The serving probe uses the API server's Pod forwarding path, binds only a
temporary loopback port, verifies the installed CA and DNS identity, and checks
the complete leaf against a fresh TLS handshake. It verifies each Pod UID
before and after the connection, rejects restarts, bounds the upgrade and
handshake, and closes its forwarding worker. Keys stay in memory. A successful
read-only probe of healthy endpoints proves that path works; it does not prove
an alert fired or recovered.

Admission recovery reads raw range-vector samples at a common evaluation
instant. Each observed counter increase brackets a real rejection between
native scrape start and completion, including the recorded scrape duration.
Its resolution deadline starts at the earlier edge of the
last bracket, so scrape uncertainty cannot grant extra time. A series first
seen at one supplies no fabricated zero or observed increase. All API servers
must have complete, healthy, fresh scrape histories through the receiver's
resolution; a missing series, counter reset, skipped scrape, or partial query
fails the proof. The receiver must resolve after the whole five-minute window
and within its additional 45 seconds. Raw histories remain in the run log.
