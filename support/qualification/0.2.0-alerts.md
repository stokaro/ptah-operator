# Alert proof inventory for 0.2.0

This inventory implements Q-09 and #581. Every row remains **Not assessed**
until its live fault, receiver delivery, recovery, and resolution pass on the
qualified identities. The [frozen profile](0.2.0.md#alert-targets) supplies each
row's threshold, start event, delivery deadline, and resolution deadline.
The [monitoring values](0.2.0-monitoring.yaml) supply the chart settings.

Run every row on each supported Kubernetes minor and runtime architecture.
Run database-specific faults on both engines and family-labeled faults on both
families. Installation-wide signals have no family label; plan storage counts
schema payloads because migration plans carry no SQL payload. Record those
dispositions explicitly.

The receiver is each alerting phase's `alert-sink`. Record its actual firing and
resolved payloads, installation labels, bounded family/operation/stage labels,
severity, runbook URL, and timestamps. Metric labels must not acquire resource,
Job, Pod, plan, or execution IDs. Keep those identities in the evidence and
runbook drill-down instead.

The phase renders the chart with `0.2.0-monitoring.yaml` over the installed
release values. All ten chart rules must retain the frozen expressions and
timing, appear exactly once, and evaluate successfully in Prometheus before a
scenario starts. Missing or unhealthy rules cannot prove an absence of false
notifications. An absence query must return an explicit instant vector; a
missing or null result is an error. This gate does not supply the external upgrade route or the
remaining live fault and negative-control rows.

Run ten-minute negative controls with ordinary approval waits and permanent
policy refusals on each family. Keep normal observation/retry cadence running;
they must not produce a failure notification. Do not weaken the incident
thresholds or exclude an affected family to make a row pass.

## State-read failure preparation

The manager now reads the two resource families and two plan kinds directly
from the API once per leader scrape, within one three-second budget. A failed
list suppresses all state gauges and increments the read-failure counter.
Followers remain unsynchronized. The API-server regression demonstrates why
RBAC loss alone did not test the old view: a warm informer still returned its
original object after the API refused the same list. The new collector reports
that refusal and recovers from a fresh API reading after access is restored.

Unit and API-server controls cover partial reads, timeout, leadership loss and
recovery. They do not prove chart-rule evaluation or receiver delivery. The
`unresolved-view-read-failures` row now revokes and restores the exact installed
list grant separately for each family. It records actual Forbidden list
responses and every manager's counter, health and scrape-duration history.
Missing or reset counters, gaps, failed scrapes, changed Pod/process identities
and leader transitions fail the proof. Receiver notifications must name the
installation and the same alert instance; native increments supply the firing
and resolution bounds. The original ClusterRole UID and complete rule set
protect both fault injection and cleanup. This row still needs a completed
native run on the final identities.

## Stalled-operation proof preparation

The two families run sequentially. Each starts with no active stalled Resolve
alert, creates its own resource, and records the exact dispatched operation,
Job and unscheduled Pod. Those identities must remain unchanged while the
scheduling gate is closed. The receiver's firing must start after the claim's
native age threshold and arrive within the frozen delivery allowance.

After the gate opens, the original executor must finish transporting a failed
Resolve result. A successful Pod proves transport completion; its exact runner
frame must separately report the failed OCI child. The original resource must
account for that attempt and defer its retry for the configured hour. Schema
records this in `Failed` with `nextReconciliationTime`; migration retains
`Resolving` with `retryNotBefore`. Neither wait counts as an operation in flight.
Every declared container needs a matching successful terminated status; a missing outcome,
restart, replacement Pod or additional executor fails the proof. Resolution is
dated from the latest native container finish, not from the later status poll.
The receiver must resolve the same incident within 105 seconds of that native
finish, and the alert must clear before the fixture is suspended. This is the
frozen stalled-operation recovery allowance, distinct from the 45-second
delivery slack used by other rows. Unit controls reject
subsecond deadline violations and an early firing hidden by delayed delivery.
These controls do not supply the remaining native matrix result.

## Certificate proof preparation

The warning fixture expires 24 hours plus five minutes after it is signed.
Its threshold therefore crosses after five minutes while admission remains
valid. A second leaf, signed under the same installed CA and serving key with
the same DNS identities, then expires after five minutes for the separate
admission fault. This avoids substituting a shorter warning threshold.

The serving probe uses the API server's Pod forwarding path, binds only a
temporary loopback port, verifies the installed CA and DNS identity, and checks
the complete leaf against a fresh TLS handshake. It verifies each Pod UID
before and after the connection, rejects restarts, bounds the upgrade and
handshake, and closes its forwarding worker. Keys stay in memory. A successful
read-only probe of healthy endpoints proves that path works; it does not prove
an alert fired or recovered.

Admission recovery reads raw range-vector samples at a common evaluation
instant. Each observed counter increase brackets a real rejection between
native scrape start and completion, including the recorded scrape duration.
Its resolution deadline starts at the earlier edge of the
last bracket, so scrape uncertainty cannot grant extra time. A series first
seen at one supplies no fabricated zero or observed increase. All API servers
must have complete, healthy, fresh scrape histories through the receiver's
resolution; a missing series, counter reset, skipped scrape, or partial query
fails the proof. The receiver must resolve after the whole five-minute window
and within its additional 45 seconds. Raw histories remain in the run log.

## Leader-scrape proof preparation

The partial-scrape row changes only the original leader's metrics path. Pod
UIDs, process identities, leader identity, addresses and public target labels
must remain stable. Native `up` and scrape-duration histories must contain the
healthy baseline, one uninterrupted leader failure, healthy followers and every
scrape through receiver resolution. A missing target, skipped scrape, changed
endpoint or second failure prevents a pass.

The first failed scrape starts the 105-second firing allowance. The first
recovered scrape starts the 45-second resolution allowance and must contain the
same leader's synchronized-view gauge. A healthy HTTP response alone does not
establish recovery. Notifications must belong to the same installation and
incident, and no early firing may be hidden by a later receiver timestamp.
Local controls cover these boundaries; the completed native matrix remains
required.


## Overdue-resource proof preparation

Each family starts with a real realm refusal and the next reconciliation time
its controller persisted. The absent realm gives both families a recheck
schedule; a failed migration operation instead carries a different retry field
and cannot establish this incident. The fixture's resource-specific admission
policy refuses both metadata and status updates. Dry-run controls require the
exact policy's Forbidden response and keep another resource writable.

The original UID, generation and deadline stay fixed past the 60-second overdue
threshold. Granting the isolated realm while writes remain refused cannot
advance the resource. After the policy is removed, a closed resource watch must
contain its new Resolve claim and a real owned workload. The claim's native
start dates the 45-second resolution allowance; reading a retained receiver
notification later does not extend it. The original managers and their scrape
health remain stable throughout. No synthetic status supplies the deadline or
recovery, and neither the registry failure after Resolve nor a suspension may
stand in for recovery. Unit controls and the production-controller transition
prove the fixture's reachability; final-identity receiver execution is pending.

## Ordinary policy waits

`ordinary-policy-waits` creates a schema and a migration under each of
`OnApproval` and `Never`, with separate empty PostgreSQL databases. It reuses
only the real artifact and execution specifications left by the migration and
reference-data producers; every control gets a new UID, no status, and a real
controller-published plan. Both producer phases are declared prerequisites.

The controls retain the profile's two-minute interval for at least ten minutes,
plus the delivery allowance. Native database-observation timestamps must advance.
Closed resource and Job watches refuse an Apply, a changed resource generation,
an accepted approval, or an unresolved result. Final reads require the databases
to remain empty. Every chart rule must keep evaluating, every manager scrape
must stay healthy, and manager, leader and monitoring process identities must
stay unchanged. Missing receiver data or a truncated journal fails the row.

The preceding scenario resolves its migration incidents before the quiet window.
The row requires no remaining unresolved resource and no active alert. Only an
exact duplicate of the already delivered resolution is excluded; a new firing,
changed count, label, receiver, start or end time, or another rule's notification
fails.
No family or failure rule is disabled. Successful cleanup removes only the
control resources, Secrets, and databases; failed runs retain their cluster.

Predicate and fixture controls do not establish execution of this row. A full
native run on the final identities remains required before acceptance.


## Complete manager-loss proof preparation

The `lost-view` row cordons the original node inventory and removes each
original manager by UID. Replacements must remain unscheduled while the
monitoring processes and all alert rules continue running. Complete native
`ALERTS` samples retain the pending-to-firing transition with no missing
evaluation. The first failed scrape of the original leader, when available,
starts the delivery deadline if it precedes that transition. Discovery may
remove a target before another scrape; in that case the native transition
supplies the start without inventing a failed scrape. Waiting for Pod deletion
cannot move either timestamp.

Recovery restores scheduling and requires new manager identities. Every
replacement's native view, health and duration samples must match, remain fresh
and cover the receiver's resolution. The first synchronized scrape of the new
leader starts the frozen 45-second resolution bound. The resolution must name
the same incident, and the leader, replacements and monitoring processes must
remain stable. Waiting for rollout or observing the notification later cannot
extend the bound. Unit controls cover missing observations, early firing,
changed incidents, unhealthy replacements and subsecond deadline violations.
Final-identity native execution remains required.


## Owed lock-release proof preparation

The `lock-release-owed` row runs PostgreSQL and MySQL, each with a PtahSchema
and a PtahMigration. It publishes each engine's migration directory with the
installed executor and uses the real reference schema artifact. Every case
starts with a fresh database and requires an actual published plan and exact
approval. The Apply Pod remains unscheduled while a policy is installed to
refuse only release of its exact Lease by the manager. Dry-run controls admit
the release before the fault, refuse it at that policy after installation,
and still admit renewal.

The authorized Apply must finish successfully and change the database. The
controller's completed result and pending release must name the original
operation and acquisition epoch. That native completion timestamp starts the
60-second pending period and 105-second delivery bound. The record, holder,
manager identities and healthy scrapes stay checked throughout the refusal.
A sibling schema may resolve and observe, but its Plan must wait for the same
realm without dispatching a Job.

Removing the fault must produce a watched empty holder on the original Lease.
Its native renewal timestamp starts the 45-second resolution bound. The same
Lease's ordered history must then show the sibling's new acquisition, and its
Plan must complete without overlapping the original executor. Closed resource,
Lease, Job and Pod histories refuse a second Apply, a replacement executor or
any Apply by the Never-policy sibling. The database table count must remain
unchanged during the sibling's read-only work. Cleanup removes only this row's
objects and databases; failed cases retain their fixtures for diagnosis.

Predicate controls and local gates support this implementation. They do not
supply the required native execution on the final artifact identities.


## Repeated operation failures

The `operations-failing` row creates an isolated database and an unchanged
Never resource for each family. Its OCI reference initially names an unpublished
artifact. At least four distinct original Resolve Jobs must return the expected
failed operation through successful, complete runner transport within one frozen
five-minute window. Each result is bound to the original claim, Job and Pod.
The families run in two concurrent lanes, with separate temporary files and
fixtures. Both lanes must finish; neither changes shared cluster settings.

A complete quiet counter window precedes the fault. Native counters, health and
scrape-duration series cover every manager, including followers. Missing samples,
resets, a changed leader, extra failures and failures in another category refuse
the proof. The alert's third native increment supplies a conservative firing
bound because PromQL `increase` extrapolates and may exceed three before a fourth
integer increment. The fourth actual result remains mandatory and cannot move
the receiver's deadline.

Recovery publishes the missing artifact at the same reference. UID, generation,
specification, policy, cadence and retry settings remain unchanged. Runner results
continue to be collected while publication runs. A successful Resolve must return
the published digest and read-only reconciliation must reach its policy gate.
The same receiver incident must resolve within the frozen bound. Observation
continues through a full quiet five-minute window after the last native failure,
even if the alert resolved earlier as older failures aged out.

Resource, Job and Pod watches close after API barriers. The closed histories
refuse Apply, extra or replaced Resolve transports, and missing results. Counter
increments must equal the retained failed Jobs. Unit controls cover both families,
healthy followers, contaminated histories, actual rolling-window counts and early
or late notifications. They do not replace final-identity native execution.

## Plan-store proof preparation

The `plan-store-large` row calibrates the pinned Ptah serializer through real
small plans, then creates seventeen 8 MiB plans under Never policy. Consumers
share one isolated PostgreSQL database and coordination key, with at most four
new consumers at once. Every payload is reconstructed from its original chunks
and checked against its manifest, digests and generated native SQL. The owned
payloads alone exceed the unchanged 128 MiB alert threshold. Migration plans
store references to artifact versions, not SQL payloads, so that family is not
applicable to this installation-wide byte signal.

The row starts its firing history before the last two plans can cross the
threshold and its recovery history from a fresh above-threshold baseline before
pruning. Both windows require the original leader, healthy followers, unchanged
monitoring identities and complete native scrape histories. Firing and resolution
retain their 45-second bounds from the native threshold transitions, even if a
later poll first notices them. The firing window ends at the receiver's delivery
timestamp plus the existing scrape-gap allowance and must include each manager's
scrape through that delivery. Finishing publication, replacement and export
cannot extend it.
Between the timing windows, the receiver must retain the original incident
without an early resolution or a new firing identity. A missing gauge during
that work cannot supply either timing boundary or hide a premature recovery
notification. The fresh pre-pruning baseline must include all owned bytes.

To recover, each consumer receives a small replacement plan and acknowledges
suspension with no operation or pending recovery in flight. The complete
runbook pin inventory includes both resource families, historical approvals,
execution-binding retirement and unresolved migration runs. Every chosen plan
is exported with its chunks, reconstructed from the stored archive, and
retained as a checksummed gzip/base64 record in the phase log before deletion.
These generated fixture exports are credential-scanned before they are logged.
The live pin inventory is checked again for each deletion, which requires the
original plan UID and resource version. Native garbage collection must remove
the chunks and projections; all remaining pins must still load their exact
payload or migration plan spec. Closed resource and Job histories refuse Apply,
and the isolated database must remain empty. Local controls exercise all pin
sources, corrupt exports, unsafe pruning and invalid timing histories. A passing
final-identity live run is still required before this row can be accepted.


## Independent unresolved-migration proof preparation

The migration phase retains the late-dispatch refusal and its SQL audit, then
finalizes that exact fixture by UID. Earlier alert checks reused its unresolved
run; these independent incidents require a zero baseline. Retirement happens
only after the refusal is proved and active work and owed lock release have
ended. It is fixture cleanup, not evidence of unknown-run recovery. Other
unresolved resources still fail the baseline and are named in the diagnostics.
The restored-history fixture is also finalized after its fresh Apply and SQL
proof, before closing its scheduler gate. Otherwise its later periodic read
would remain unschedulable and raise an unrelated stalled-operation alert.
Both fixtures retain private resource, Job, Pod and SQL-count evidence outside
the phase's temporary directory; collect the paths and digests from the phase log.

The `unresolved-apply` row creates an isolated migration consumer on each of
PostgreSQL and MySQL. A native approval authorizes the sequence. Its first two
migrations must have committed before the original Apply Job is removed by UID
while the last migration still runs. Monitoring and direct resource, Job and Pod
watches start before the incident. Another unresolved migration at baseline
fails the row because the family-wide rule could otherwise mask this fault.

The native leader gauge must move from zero to exactly one, with complete healthy
scrapes from every replica. The receiver must report that count, installation,
family, critical severity and the existing runbook. The original `recordedAt`
bounds delivery to 45 seconds; a later status read or metrics scrape cannot
move the deadline.

Recovery first requires retirement of the original claim, stopped or absent
original Pods, no remaining application-user database session, and inspection
of the two committed migrations and their three data rows. The third migration
only sleeps, so after its executor stops its unfinished revision can be removed
without undoing any database effect. The installed approver role authorizes a
named acknowledgment of that exact run. A fresh history reading and a new plan
for version 3 must precede a new approval. Closed workload histories forbid any
Apply before that approval and any extra Apply during the positive recovery.

The resolved notification must belong to the original incident and arrive within
45 seconds of the controller's `resolvedAt`. Native samples must show the gauge
returning to zero while the same leader, followers and monitoring processes remain
healthy. The subsequent negative controls start with no unresolved records or
active alerts. Local refusal controls cover both retained native engine records,
missing and corrupted metric histories, altered recovery copies, late delivery,
and the distinction between a historical run and fresh authorization.

Schema cases use separate databases on both engines. A table lock holds the
approved DDL while its original Pod is running. The resource is suspended and
its Job is removed by UID. The first persisted Applying-to-Unknown transition
starts the firing bound. The original executor must stop, its database session
must disappear, and the retained data and absent new column must be inspected
before the table lock is released. Only that original session may be terminated
if MySQL retains queued DDL after its client exits.

Resuming allows read-only Observe and Plan against the original immutable
binding, after the persisted execution horizon. A closed status history must
show both dispatched Jobs before Unknown clears. Its first completed Plan
result dates resolution; later refreshes cannot move the deadline. Workload
histories forbid another Apply until a new approval, and the database must
still have its original data and no new column at that boundary. A fresh
approval must then add the column without changing those rows.

Local refusal controls accept claims before their Job UID is assigned and
incremental discovery of the original executor Pod. They reject missing reads,
changed bindings, shortened execution horizons, replacement Pods, premature
clearing and replay. Fixture policy changes retain each producer's lock timeout;
the generated CEL rule is checked against their serialized values and the
explicit `0s` value that API defaulting cannot repair.

This implementation does not supply a native pass. Final-identity runs and the
other open rows in the incident table remain required. Thresholds, the 30
functional cells, the 36 recovery combinations and every operating target remain
unchanged.

## External upgrade route

`upgrade-alerts` runs last because it stops and replaces the operator runtimes.
It loads the observer rules into the existing Prometheus and Alertmanager, checks
the effective expressions with that Prometheus image's parser, and compares the
real receiver timestamps with native Job and workload events. A successful hook
alone cannot resolve an incident. The retry must restore the exact candidate
CRDs, owned ready runtime Pods, admission, and fresh read-only progress for
Schema and Migration on PostgreSQL and MySQL. Continuous histories refuse any
Apply or change of probe identity, generation or specification.

The failed-hook fault denies a runtime update by the hook's own identity. It
therefore exercises the hook even when the installed CRD bytes already match
the candidate. Both incidents require an actual `Deleted` event for the original
hook UID in the independent history; a deletion timestamp alone is insufficient.
The separate interruption permits the hook but denies Helm's
runtime restoration. The original prepared deadline survives the retry.

The observer is outside the upgraded Helm release, in the phase's monitoring
namespace. The row refuses observer or monitoring process replacement. Its
EmptyDir state is scoped to that controlled lifetime; this does not qualify
observer Pod loss, cluster loss or the durable operational deployment described
in `hack/upgradealert/README.md`. The phase backstop is 105 minutes to accommodate
the added fifteen-minute incident and its preparation and retries. The incident
threshold and both 45-second receiver bounds are unchanged. No native pass is
recorded by adding this scenario.

The controlled run retains its exact chart, values, Helm invocations and output,
observer states, effective monitoring configuration, hook histories, closed
probe and workload histories, recovery CRDs and runtime identities, admission
dry-run responses, receiver payloads and checksums in a private `ptah-e2e-upgrade-evidence.*` directory. Its
path is recorded in the phase log. Collect this directory into the restricted
evidence inventory before retiring the execution host; a CI success whose
private bundle was not retained does not supply the final qualification record.

The CI catalog partitions these existing scenarios across three clusters.
`alerting-operations` runs unresolved Applies, ordinary policy waits, stalled and
overdue operations, lock release, and repeated failures. `alerting` runs plan
storage, failed state reads, scrape loss, manager loss, and upgrade faults.
`alerting-certificates` runs certificate expiry in the certificates suite. Each cluster prepares its native producers and monitoring path.
Every incident and its original detection, recovery, and quiet-window bounds
remain mandatory. The split changes scheduling, not acceptance targets.
