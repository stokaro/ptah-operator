# Capacity input verification

`probes/capacity_fixtures.py` prepares the SQL inputs for the workload in
[the frozen profile](0.2.0.md). Each logical slot has 10,000 deterministic
rows. PostgreSQL schema changes alter executable defaults. MySQL schema
changes add tables with executable defaults and preserve all earlier tables.
Both cover the small, medium and large plan bands. Migration directories contain real up/down SQL with initial
histories of 2, 32 and 128 versions.

Before using those inputs in an operator run, execute them with the Ptah
commit pinned in `support/ptah.json` on both database engines:

```sh
python3 support/qualification/probes/capacity_fixture_verify.py \
  --engine postgresql \
  --docker-context remote-dev-container \
  --ptah-binary /absolute/path/to/ptah-linux-amd64 \
  --ptah-sha256 "$PTAH_BINARY_SHA256" \
  --output /absolute/path/to/new-postgresql-results

python3 support/qualification/probes/capacity_fixture_verify.py \
  --engine mysql \
  --docker-context remote-dev-container \
  --ptah-binary /absolute/path/to/ptah-linux-amd64 \
  --ptah-sha256 "$PTAH_BINARY_SHA256" \
  --output /absolute/path/to/new-mysql-results
```

Build the binary from the pinned source for the Docker host's architecture.
Record its source/build identity and checksum before running the probe. The
probe verifies those binary bytes after copying them to the container; the
checksum alone does not establish the source commit. The digest-pinned database
images from `probes/database_restore.py` must already be cached on that host.

Use `--suite schemas` or `--suite migrations` for a focused rerun. The report
records that selection; success applies only to the selected suite. Keep failed
attempts beside their reruns.

Each invocation creates one database container with networking disabled,
1 CPU and 1 GiB of memory. Ptah and the SQL client run inside it. Each fixture
uses a separate database owner, with no global database privileges. Cleanup
checks the container's run label and removes only that container and its
anonymous volumes. It does not pull images or prune the shared Docker host.

The report retains the procedure hashes, source status, binary and image
identities, native plans, migration checksums, command results, complete row
inventories and cleanup result. Output is private because error messages and
container metadata can include the disposable credentials. Do not publish the
raw directory without reviewing it for credentials.

For each schema band, all ten versions must produce nonempty, nondestructive
native plans inside the declared byte range. Before Apply,
`hack/capacityplancheck` passes the saved plan through the operator's own
classification and refuses destructive or privilege changes. Ptah's safe
metadata alone is insufficient: MySQL default edits render `MODIFY COLUMN`,
which the operator conservatively treats as destructive.

The probe measures the saved
plan, including Ptah's descriptions of old defaults, and recalibrates each
transition when needed. It executes each plan, evaluates every new default
inside a rolled-back transaction, and compares all 10,000 original rows byte
for byte. Failed calibration attempts remain in the output.

For each migration history, the probe applies all but the last version,
loads the rows, verifies the exact applied/pending version lists, applies the
pending version, and verifies every row and added column default. Histories
starting at 2 and 32 receive nine further versions. The 128-version history
stays at the profile's maximum. No missing, reordered, duplicated or changed
row is accepted as an intact inventory.

The [recorded Linux amd64 input checks](evidence/capacity-inputs-2026-10-01.json)
cover both engines and retain the failed attempts as well as the successful
sections and reruns.

This is input verification. It does not run an operator, publish OCI artifacts,
measure capacity, execute the 90-minute soak or supply a cell of the required
Kubernetes/engine/architecture matrix. #580 remains open until the complete
workload and measurements satisfy the frozen profile.

The first populated MySQL operator run exposed that default-edit mismatch.
The [failure and corrected input results](evidence/capacity-mysql-input-fix-2026-10-01.json)
retain both attempts. Its ten migration resources converged, while all ten schema resources stopped
at the destructive-change gate. That failed run does not establish MySQL
capacity or restart recovery. The additive fixture corrects the input without
changing the operator policy.

## Run the inputs through the operator

With a disposable lab running, enable the populated inputs in the capacity
harness:

```sh
CAPACITY_VARIED_INPUTS=1 CAPACITY_OUT_DIR=/absolute/path/to/new-results \
  ./hack/capacity.sh
```

For the frozen separation-of-duties profile, install the chart with
`approvals.requireDistinctApprover=true` and set `CAPACITY_AUTHOR_KUBECONFIG`
and `CAPACITY_APPROVER_KUBECONFIG` to separate, same-cluster identities. The
author must differ from the installation administrator and the approver.
Keep `approverClusterRole.create=true` on the chart. The bootstrap copies the
Role from `examples/desired-state-author-role.yaml` into its two new workload
namespaces and binds it to the authenticated author. It binds the chart's
approver role only in those namespaces. It creates no ClusterRoleBinding.

Set `CAPACITY_WORKLOAD_NAMESPACES=ptah-qualification-a,ptah-qualification-b`
to use the frozen profile's namespace names. Both must be absent before the
run. The bootstrap creates and journals their UIDs and refuses to adopt or
delete an existing namespace. Without this setting, lab runs keep their
generated namespace names.

The capacity command also accepts `-author-kubeconfig` and
`-approver-kubeconfig` directly. When bypassing the bootstrap, create the
namespace Roles and RoleBindings first. The command verifies API usernames
through SelfSubjectReview and refuses reused identities or a different API
endpoint. An author configuration requires an approver configuration.

The author creates desired state, changes inputs, moves resources to approval,
and deletes and replaces workload resources during churn. For `Always`, the
author first creates a suspended `OnApproval` resource, the administrator
selects `Always`, and the author resumes it. Each patch retains the original
UID and resourceVersion. Refusal before resumption leaves the resource
suspended; a lost write response fails the run without replaying the write.
This preserves the chart's apply-policy guard and the authenticated spec writer.
Only the approver creates approvals. Measurements and installation/maintenance
keep their original credentials. The report records the API-confirmed
`installer`, `workloadWriter`, and `approver` in `approvalActors`.

Without these options, the existing lab client still performs workload and
approval writes. A separate approver alone proves approval separation, but
neither mode establishes the frozen profile's ordinary author permissions.

Generated workloads use the frozen execution baseline: a 900-second operation
deadline, a 10-second connection timeout, and 30-second retry and lock timeouts
for both resource families. Fault-specific changes remain explicit in their
recorded resource specifications.

For the frozen registry profile, first provision the existing authenticated TLS
registry fixture and an immutable CA ConfigMap in the lab namespace. Set
`CAPACITY_REGISTRY_HOST` to its DNS authority and port, and
`CAPACITY_REGISTRY_CA_CONFIGMAP` to that ConfigMap, whose bundle key is `ca.pem`.
The bootstrap copies the CA into both workload namespaces and binds the registry
credential to that authority and the exact CA digest. The capacity client then
uses HTTPS with `caFrom`; it does not grant plain HTTP for those artifacts.
Container pull credentials remain separate from artifact credentials.

Set `CAPACITY_SIGNING_KEY` and `CAPACITY_SIGNING_PUBLIC_KEY` to a temporary
Cosign key pair, and provide `COSIGN_PASSWORD` for the private key. Use Cosign
3.0.6, the version in the pinned release installer; `CAPACITY_COSIGN` can name
its binary. Varied-input preparation signs each published digest, verifies it
with the public key, and retains the verification output and key digest before
populating any database. The immutable workload policies require digest pins
and attached signatures. Ptah's policy checks signature presence; the preceding
Cosign verification establishes the cryptographic check.

The signer uses Cosign's explicit OCI 1.1 signature format recognized by the
pinned Ptah, not the default Sigstore bundle referrer. Publication and signing
use the private lab tunnel; artifact consumption uses the HTTPS authority.
The temporary key and private registry do not use public transparency services.
Without these inputs, the existing unsigned HTTP lab remains a development
measurement and cannot establish the frozen registry profile.

The workload must declare ten resources of each family and a `changeBatch` of
zero or five. The harness publishes digest-addressed artifacts to the lab's
registry, applies each migration history's prefix with the pinned Ptah, and
loads and verifies 10,000 rows per database before creating operator resources.
It refuses a target Secret that names a different database endpoint or owner.

Before populating the databases, the harness reads back every artifact from the
lab registry tunnel. It verifies the manifest digest and each blob's actual
size and digest, and compares migration files with the published source. The
canonical schema layer is HCL, so its payload size comes from the downloaded
bytes rather than the SQL input. Ptah's file layers are uncompressed: stored
and unpacked payload bytes are equal, and the inventory records that encoding.
An empty, duplicate, mismatched, unsupported or oversized file inventory fails
preparation. Raw manifests and content-addressed blobs remain under `inputs/oci`;
`bundle.json` records their sizes and bindings. All files stay private with the
rest of the workload evidence.

`support/capacity/input-calibration.json` binds the executable defaults to the
verified generator and Ptah commit. It was measured again on October 10, 2026
with the Ptah v0.13.0 release binary, when the executor moved to that release:
both engines passed every schema band and migration history, PostgreSQL plans
needed up to eight more repeated characters per band, and MySQL plans were
unchanged. The two reports are retained with the 0.2.0 evidence. After cold convergence and the change batch,
the driver reads each applied plan from the committed plan store and verifies
its actual size and Apply projections. The report retains the plan manifests,
UID bindings, byte counts and catalog digest. A calibration estimate cannot
substitute for these reads.

After the driver finishes, the harness rereads every original row, executes
schema defaults inside rolled-back transactions, and checks the exact native
migration history and populated column values. `inputs/database-verification.json`
is written only after all twenty databases pass. A failed check fails the harness
before cleanup; partial readings remain in the private output directory.

While the owned databases are still running, the same verifier can retain a
separate inventory for any prepared round:

```bash
python3 support/qualification/probes/capacity_workload.py \
  --state /absolute/path/to/results/bootstrap-state.json \
  --directory /absolute/path/to/results/inputs \
  --verify-changed 5 --verify-round 9 --checkpoint round-09-after-update
```

`--verify-round` selects the version expected in the first five slots of each
family; the other slots still require version zero. `--verify-changed 0` checks
version zero everywhere. Each checkpoint retains all twenty row inventories,
schema defaults, migration histories and the prepared bundle's SHA-256 under
`inputs/checkpoints/<name>`. Reusing a checkpoint or a legacy output directory
with partial or complete database evidence fails before querying the databases.
A failed checkpoint keeps its readings and has no success record.

The default lab workload executes one change batch. The soak workload uses all
nine prepared update versions:

```bash
CAPACITY_VARIED_INPUTS=1 CAPACITY_WORKLOAD=support/capacity/soak.json \
  CAPACITY_OUT_DIR=/absolute/path/to/new-results ./hack/capacity.sh
```

It runs for 90 minutes after cold convergence. Each fixed ten-minute window
updates five resources per family, verifies every database, replaces two idle
resources per family, and verifies the databases again. Each round also verifies
its starting data. Updates and replacements retain the current immutable
artifact references and database targets. A missed window fails instead of
moving the remaining deadlines. Cold and update convergence are measured from
the first submitted write, with original UID and generation bindings.

Replacement deletes carry both UID and resourceVersion preconditions. A conflict
causes a new read and a separate export; an unexpected replacement stops the
run. Before deleting an owner, the driver exports its plans, committed chunks,
available Apply projections and verified reconstructed payloads under `churn/`.
It waits for owner garbage collection and records the old and new resource UIDs.
The new resource copies only the current spec and workload label. A migration
already at its desired history can legitimately own no plan; the export records
that count and still requires every live pin to resolve.

The report retains all database checkpoint digests and replacement identities.
At least 30 complete read-only cycles must belong to each logical slot across
its recorded UID lifetimes. Every incarnation present for two refresh intervals
must complete a cycle. Missing watches, unrecorded replacements, unfinished
rounds, stale checkpoint data and missing garbage collection fail the run.
Shorter diagnostic configurations must declare their actual duration, cadence,
rounds and minimum cycle count; they do not qualify the 90-minute profile.

Each round also exports plans, suspends the full fleet, waits for terminal Jobs
and Pods, and re-reads all retention pins before UID/RV-bound pruning. It waits
for plan garbage collection, verifies pinned bytes, samples the same running
managers, then resumes and checks convergence and all databases. The final three
maintenance checkpoints must have non-growing payload within 128 MiB and RSS
within 192 MiB per process and 10% of their first checkpoint.

The soak now runs the unrelated-object population, the pending-approval and
unresolved-Apply retention fault, the three-minute registry outage and the
thirty-second database delay. The within-fleet approval backlog is
`support/capacity/backlog.json`, and the forty-resource overload is
`support/capacity/overload.json`; each has a MySQL twin. The plan beyond 8 MiB is
the data-plane suite's `native-plan-size-boundary` row. Its restart approval
fixture is still a twenty-first database. Implementing these scenarios does not
close #580 or establish the complete frozen profile; completed runs on the
qualified artifacts do.

The run finished with exit code zero, and cleanup was independently verified.

## Run the frozen-profile matrix

`probes/profile_lab.py` builds one lab to the frozen installation contract and
measures one workload in it: the harness bootstrap on the prepared release's
digests, native installer/author/approver identities with the chart
reinstalled in a restricted `ptah-system` with a distinct approver, the
corrected kindnet, the registry TLS fixture, the capacity namespaces and signed
populated inputs, the documented egress policies with 24 live allowed and denied
traffic controls, and a preflight of host capacity, kubelet log size, Pod
Security, quota, managers and CNI. The measurement runs from a toolbox container
in the control-plane node's network namespace, built from `git archive` of the
harness commit; its evidence is copied back only when it matches its own
checksum manifest.

`probes/capacity_matrix.py` runs every supported minor, both engines and the
soak, backlog and overload workloads on one host, one fresh lab each:

```sh
python3 support/qualification/probes/capacity_matrix.py \
  --context diabolocom --release-manifest /path/to/release-manifest.txt \
  --out /private/path/capacity-amd64
```

One host is one architecture; run it again on a native host of the other. A
failed cell is recorded with the step it stopped at, and the matrix continues.
