# Capacity input verification

`probes/capacity_fixtures.py` prepares the SQL inputs for the workload in
[the frozen profile](0.2.0.md). Each logical slot has 10,000 deterministic
rows. PostgreSQL schema changes alter executable defaults. MySQL schema
changes add tables with executable defaults and preserve all earlier tables.
Both cover the small, medium and large plan bands. Migration directories contain real up/down SQL with initial
histories of 2, 32 and 128 versions.

Before using those inputs in an operator run, execute them with the Ptah
commit pinned in `support/ptah.json` on both database engines:

```sh
python3 support/qualification/probes/capacity_fixture_verify.py \
  --engine postgresql \
  --docker-context remote-dev-container \
  --ptah-binary /absolute/path/to/ptah-linux-amd64 \
  --ptah-sha256 "$PTAH_BINARY_SHA256" \
  --output /absolute/path/to/new-postgresql-results

python3 support/qualification/probes/capacity_fixture_verify.py \
  --engine mysql \
  --docker-context remote-dev-container \
  --ptah-binary /absolute/path/to/ptah-linux-amd64 \
  --ptah-sha256 "$PTAH_BINARY_SHA256" \
  --output /absolute/path/to/new-mysql-results
```

Build the binary from the pinned source for the Docker host's architecture.
Record its source/build identity and checksum before running the probe. The
probe verifies those binary bytes after copying them to the container; the
checksum alone does not establish the source commit. The digest-pinned database
images from `probes/database_restore.py` must already be cached on that host.

Use `--suite schemas` or `--suite migrations` for a focused rerun. The report
records that selection; success applies only to the selected suite. Keep failed
attempts beside their reruns.

Each invocation creates one database container with networking disabled,
1 CPU and 1 GiB of memory. Ptah and the SQL client run inside it. Each fixture
uses a separate database owner, with no global database privileges. Cleanup
checks the container's run label and removes only that container and its
anonymous volumes. It does not pull images or prune the shared Docker host.

The report retains the procedure hashes, source status, binary and image
identities, native plans, migration checksums, command results, complete row
inventories and cleanup result. Output is private because error messages and
container metadata can include the disposable credentials. Do not publish the
raw directory without reviewing it for credentials.

For each schema band, all ten versions must produce nonempty, nondestructive
native plans inside the declared byte range. Before Apply,
`hack/capacityplancheck` passes the saved plan through the operator's own
classification and refuses destructive or privilege changes. Ptah's safe
metadata alone is insufficient: MySQL default edits render `MODIFY COLUMN`,
which the operator conservatively treats as destructive.

The probe measures the saved
plan, including Ptah's descriptions of old defaults, and recalibrates each
transition when needed. It executes each plan, evaluates every new default
inside a rolled-back transaction, and compares all 10,000 original rows byte
for byte. Failed calibration attempts remain in the output.

For each migration history, the probe applies all but the last version,
loads the rows, verifies the exact applied/pending version lists, applies the
pending version, and verifies every row and added column default. Histories
starting at 2 and 32 receive nine further versions. The 128-version history
stays at the profile's maximum. No missing, reordered, duplicated or changed
row is accepted as an intact inventory.

The [recorded Linux amd64 input checks](evidence/capacity-inputs-2026-10-01.json)
cover both engines and retain the failed attempts as well as the successful
sections and reruns.

This is input verification. It does not run an operator, publish OCI artifacts,
measure capacity, execute the 90-minute soak or supply a cell of the required
Kubernetes/engine/architecture matrix. #580 remains open until the complete
workload and measurements satisfy the frozen profile.

The first populated MySQL operator run exposed that default-edit mismatch.
The [failure and corrected input results](evidence/capacity-mysql-input-fix-2026-10-01.json)
retain both attempts. Its ten migration resources converged, while all ten schema resources stopped
at the destructive-change gate. That failed run does not establish MySQL
capacity or restart recovery. The additive fixture corrects the input without
changing the operator policy.

## Run the inputs through the operator

With a disposable lab running, enable the populated inputs in the capacity
harness:

```sh
CAPACITY_VARIED_INPUTS=1 CAPACITY_OUT_DIR=/absolute/path/to/new-results \
  ./hack/capacity.sh
```

The workload must declare ten resources of each family and a `changeBatch` of
zero or five. The harness publishes digest-addressed artifacts to the lab's
registry, applies each migration history's prefix with the pinned Ptah, and
loads and verifies 10,000 rows per database before creating operator resources.
It refuses a target Secret that names a different database endpoint or owner.

Before populating the databases, the harness reads back every artifact from the
lab registry tunnel. It verifies the manifest digest and each blob's actual
size and digest, and compares migration files with the published source. The
canonical schema layer is HCL, so its payload size comes from the downloaded
bytes rather than the SQL input. Ptah's file layers are uncompressed: stored
and unpacked payload bytes are equal, and the inventory records that encoding.
An empty, duplicate, mismatched, unsupported or oversized file inventory fails
preparation. Raw manifests and content-addressed blobs remain under `inputs/oci`;
`bundle.json` records their sizes and bindings. All files stay private with the
rest of the workload evidence.

`support/capacity/input-calibration.json` binds the executable defaults to the
verified generator and Ptah commit. After cold convergence and the change batch,
the driver reads each applied plan from the committed plan store and verifies
its actual size and Apply projections. The report retains the plan manifests,
UID bindings, byte counts and catalog digest. A calibration estimate cannot
substitute for these reads.

After the driver finishes, the harness rereads every original row, executes
schema defaults inside rolled-back transactions, and checks the exact native
migration history and populated column values. `inputs/database-verification.json`
is written only after all twenty databases pass. A failed check fails the harness
before cleanup; partial readings remain in the private output directory.

The catalog prepares nine update versions, but the current lab driver executes
only one change batch. This mode does not implement the full soak, churn,
within-fleet approval backlog, retention or overload scenarios. Its auxiliary
approval fixture is still a twenty-first database. These limits apply even when
the harness exits successfully.

The [recorded PostgreSQL operator run](evidence/capacity-populated-inputs-2026-10-01.json)
passed on Kubernetes 1.37.0 / native Linux amd64: twenty populated databases,
fifteen applied schema plans across the three byte ranges, ten native migration
histories, manager replacement and one change batch. Independent readback verified
all stored chunks and projections and forty complete 10,000-row inventories.
The report retains the scope limits above; it is not full #580 acceptance.

The [corrected MySQL operator run](evidence/capacity-populated-mysql-2026-10-01.json)
passed on source `c5e42956`, Kubernetes 1.37.0 / native Linux amd64. All ten
schemas applied with destructive changes disabled. Cold convergence took 83
seconds, recovery after manager replacement took 90.556753 seconds, and the
ten-resource update took 143 seconds. Independent readback verified fifteen
applied plans, forty complete row inventories, all twenty terminal recovery
Jobs, and all 51 published workload artifacts. All 36 metric samples contained
both managers and all three API servers; no sample or watch gap was reported.
Cleanup was verified.

The latest PostgreSQL CI report on source `1fcdde7e` still exceeded the frozen
restart target: 187.385885574 seconds against 180 seconds. Its twenty terminal
post-fault Jobs were independently verified. The MySQL result does not resolve
that finding or establish the remaining qualification matrix.
